## C++ code style

Follow the [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html) for new and changed C++ code. Keep the migrated first-party sources consistent; do not reintroduce compressed statements or inconsistent names.

- Format changed C++ files with `clang-format -i --style=file` using the root `.clang-format`: Google base, two-space indentation, 80-column limit, spaces instead of tabs and braces around control-flow bodies. Use clang-format >=15; migration was validated with 23.1.3. `./scripts/format.sh` formats all first-party C++; `./scripts/format.sh --check` verifies it without edits. Do not pack multiple statements, branches or function bodies onto one line.
- Use descriptive names: `UpperCamelCase` types/functions, `snake_case` variables, `kUpperCamelCase` constants and trailing underscores for private data members. Formatting does not enforce naming or design rules; review them separately.
- Make headers self-contained, include dependencies directly, use guards for new headers and follow Google's include grouping/order. Avoid global `using namespace` directives.
- Keep functions focused, ownership explicit and interfaces readable. Explain non-obvious decisions and invariants in comments.
- Repository exceptions: retain `.cpp`/`.hpp` extensions and current exception-based error handling. Preserve serialized content IDs and saved-world compatibility during symbol renames.
- Migrate legacy code in reviewable changes. Keep broad formatting/renaming separate from gameplay changes; do not reformat third_party or generated files. Run relevant checks after refactoring.

## Implementation
- Local collision geometry stays in 2D. The user authorized freight carts following existing explicit player roads, with bounded local town connectors. General off-road long-distance routing, armies and autonomous destination discovery remain deferred until broader command systems for owned/foreign residents and professions exist. Local gather/plant orders and road freight do not establish this broader prerequisite. Track navigation separately from collision work. Off-camera simulation covers resident work and road freight only, using a main-thread event queue and bounded service terrain requests independent of the camera. Ordinary NPC movement, animals and combat stay in the player-active area. Keep work/freight on paused simulation time, persist event deadlines, and keep all authoritative mutations on the render thread. Do not add a thread pool or offline progression without a separate discussion.
- Read relevant source and content before changing behavior. Stable content IDs and NPC IDs are part of saved-world compatibility.
- Skill dependencies are defined in `Skills()` and shared by authoritative learning and the tree. New unlocks must check the full ancestor branch, including research prerequisites; never enforce this only in UI. Keep already earned save flags when changing dependencies. Craft catalogue availability must use the same read-only requirements quote as queue construction.
- Keep authoritative quests, rewards, equipment allocation and progression deterministic. Language-model output cannot mutate game state.
- GPU work stays on the render thread. World generation stays on the worker. Do not reconfigure global world metadata while that worker is alive.
- Save atomically, support older saves, and preserve a backup before a schema migration. Never reset an existing user's progression.
- Dead residents are persistent tombstones, never recreated by roster synchronization; assigned weapons/clothes are destroyed without drops. Captive gear remains allocated until ransom returns the same instances. There is no separate hero in resident-control campaigns; selected resident death follows the same rule.
- Production uses persisted active-world runtime supplied by `std::chrono::steady_clock`, including paused menus and inactive/minimized windows; never feed it clamped movement dt or tick it twice from simulation. Growing, deliveries and tribute use paused simulation time. Neither clock includes offline/closed-world elapsed time. Roads are explicit player polylines; validate the full route and cost before one atomic construction action. Connected facilities must remain inaccessible through hostile endpoints/transit towns.
- Equipment uses counted instances. Equipped or citizen-assigned instances cannot be simultaneously allocated elsewhere. Weapons have no durability and are not consumed by attacks; ranged ammunition remains consumable.
- Starting state traits are shared by every controlled resident, including immigrants; never overwrite `Save.state_trait` from the selected resident compatibility background. Preserve stable trait content IDs and migrate earlier first-resident choices without re-awarding coins.
- State skills/recipes/technologies/exploration are shared; warehouses are per city and cargo/gear/health/position are per resident. Legacy root player/inventory fields are a compatibility view of the selected resident, never a second actor or duplicated inventory; synchronize before switching and writing saves.
- Preserve the closed money ledger across state/city/regional accounts and reserved fees/order payments. No project or passive-job coin minting. Canceling an order refunds its actual escrow once; never pay own-city projects from the state treasury to itself.
- Normal setup/launch must never delete saves. The user explicitly requested a one-time deletion of old workspace worlds for the resident-control overhaul; future test worlds stay isolated under temporary directories.
- New and changed menu controls must support keyboard focus through the shared `UiActivate` navigation layer, with visible focus and hints. Keep native arrow/Enter navigation, Tab/Shift+Tab widget traversal, modal input isolation and stable action identities; Enter must never activate both a focused control and a default action. Map keyboard plotting must use the same authoritative road/note actions as the mouse.
- Default to windowed mode. Fullscreen must be explicitly selected; respect the tiling window manager.

## Validation
Keep validation proportional to the change. Build and run affected core tests; run `ctest --test-dir build --output-on-failure` once after the final related changes. For UI changes, use a short focused real-window smoke and inspect a relevant raylib screenshot. `scripts/world-smoke.py` defaults to a quick check; extended UI workflows are opt-in for changes to those workflows or release preparation. Do not repeat long idle simulations after cosmetic or small reversible edits.

Performance measurements are occasional, not a mandatory check for every rendering/simulation edit. Measure when there is an observed slowdown or a credible new load: major rendering/geometry algorithms, near-3D graphics, large asset/actor counts, lighting or model integration. Start with one 5–10 second sample after the final changes; use longer scenarios only when the result or a specific regression calls for them. Keep 60 FPS and a worst-window p95 ceiling of 30 ms as development targets; do not spend routine iteration analyzing p95/p99. Log aggregates and meaningful events, not every function call.
